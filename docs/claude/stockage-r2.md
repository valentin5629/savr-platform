# Stockage R2 — détail et niveaux de preuve

- **Stockage fichiers volumineux** : Cloudflare R2 (URLs pré-signées), référencés via `shared.fichiers`. **Un bucket par environnement** (décision Val 2026-10-07) : `R2_BUCKET_NAME` = `savr-dev` (aperçu + local) ou `savr-prod`, obligatoire, **aucun repli**. La nature du fichier est un **dossier** de la clé (`bordereaux/`, `rapports/`, `attestations/`, `factures/`, `syntheses/`, `photos/collectes/`, `logos/`), jamais un bucket. **Aucun nom de bucket en dur** : `uploadObject` / `getObject` (`@savr/shared/src/r2/`) n'en prennent pas, les lecteurs refusent une clé d'un autre bucket (cliquets : `packages/shared/src/r2/upload.test.ts` pour l'envoi et la structure, `packages/plateforme/src/lib/pdf/r2-client.test.ts` pour la lecture). ⚠ Le code ne fait qu'aiguiller chaque environnement vers son bucket ; il ne rend pas dev incapable d'atteindre le stockage de prod. Cette étanchéité tient à la clé d'API R2 de chaque environnement, à restreindre à son seul bucket chez Cloudflare (action Val, hors code ; état ci-dessous). **État au 2026-10-09, en trois niveaux de preuve à ne pas confondre.** (1) **Mesuré** : la clé de `.env.local` écrit, relit et supprime un objet dans `savr-dev`, et reçoit un refus 403 sur `savr-prod` pour la lecture du bucket, le listage, la lecture d'un objet et l'écriture ; GitHub ne porte aucun secret ni variable d'Actions (0 pour le dépôt et pour chacun de ses trois environnements). (2) **Confirmé par Val, non mesuré** : Vercel Production utilise le jeton `savr-prod-storage`, Vercel Preview le jeton `savr-dev-storage`, chacun limité à son seul bucket ; la clé de `.env.local` est ce même jeton `savr-dev-storage` ; les trois anciens jetons ont été supprimés le 2026-10-09 ; ni Railway ni Supabase ne portent de secret R2. Le périmètre d'un jeton se règle chez Cloudflare. Pour `savr-dev-storage`, le refus sur `savr-prod` est celui que mesure le point (1), sous réserve de cette identité entre le jeton et la clé mesurée ; le périmètre de `savr-prod-storage` n'est mesuré par rien. (3) **Non testé** : la clé de production, et la valeur de `R2_BUCKET_NAME` dans Vercel (production comme aperçu). Aucun envoi n'est constaté en prod à cette date (la base n'y référence aucun fichier : 0 ligne `shared.fichiers`, aucune colonne `*_url` renseignée) ; la production ne sera éprouvée qu'au premier envoi réel, qui prouvera qu'elle écrit dans `savr-prod`, pas qu'elle est refusée sur `savr-dev`. En matière d'étanchéité, la seule mesure porte donc sur la clé de `.env.local`, telle qu'elle était ce jour-là : la refaire après tout changement de clé. Ne rien écrire ni supprimer sur R2 en supposant une étanchéité que cette mesure ne couvre pas, notamment : aperçu Vercel vers `savr-prod` (ce cas repose sur les confirmations de Val : aucune mesure n'est faite depuis l'aperçu), production vers `savr-dev`, suppression sur `savr-prod` (non tentée), tout autre bucket du compte.
